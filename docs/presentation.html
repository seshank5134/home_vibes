Problem Statement & Innovation

The Indian DIY Meal Kit Model

  • Traditional Bottleneck: In cooked food delivery, 60% of total delay is caused by restaurant kitchen cooking and packaging backlogs (45-60 min wait).
  • Direct Vendor Raw Material Hubs: HomeVibes sources fresh produce, farm paneer, pre-marinated cuts, and whole spice pouches directly from local vendors.
  • Instant Dispatch: Kits are sealed and dispatched in under 2 minutes—eliminating food spoilage and restaurant preparation wait.
  • Step-by-Step Chef Cooking Scripts: Customers follow our 4-step chef scripts with flame and timing guides, cooking hot homestyle meals at home in 15 minutes.
  • Currency & Pricing: Complete ecosystem natively priced in Indian Rupees (₹) with standard ₹40 hub delivery fee.
Speaker Notes: "Our architectural innovation is business agility: raw materials are packed immediately at supply hubs, cutting transit latency while delivering fresher food to customers."
System Architecture

Three-Tier Decoupled Cloud Topology

1. Customer Web Application (Port 3000)

Explore meal kits, view sealed raw ingredient manifests, read cooking scripts, checkout in ₹, and track orders on live maps.

2. Driver Mobile Edge Client (Flutter Android)

Streams real-time throttled GPS coordinates over WebSockets, manages online shift availability, and updates delivery states.

3. Kitchen Hub Admin Console (Port 3001)

Live order dispatches queue, driver fleet management, meal kit availability toggles, and revenue tracking in ₹.

4. Managed Cloud Backend (Supabase PaaS)

PostgreSQL 15 (10 relational tables), Row-Level Security, Change Data Capture over WebSockets, and Serverless Edge Functions.

Clients (Web/Mobile) │ [HTTPS/WSS] ▼ Supabase PaaS (PostgreSQL 15) ├── 10 Relational Tables (3NF) ├── Row Level Security (RLS) ├── Realtime WAL Change Stream └── Deno Serverless Edge Functions
Speaker Notes: "Our three client tiers are completely decoupled and interface with the managed PostgreSQL backend over secure HTTPS REST and WebSocket connections."
Cloud Service Models

NIST Cloud Computing Service Model Mapping

IaaS (Infrastructure as a Service)

Underlying Amazon Web Services (AWS) EC2 compute instances, VPC networking, EBS SSD storage, and hypervisor management.

PaaS (Platform as a Service)

Supabase managed PostgreSQL: automated zero-downtime replication, connection pooling via PgBouncer, automated WAL backups.

FaaS (Function as a Service / Serverless)

Deno/TypeScript Edge Functions execute on-demand without persistent servers: price verification, order generation, driver matching.

SaaS (Software as a Service)

Customer Ordering Portal and Hub Operations Management Console delivered directly to end users via standard web browsers.

Database Engineering

Relational Schema & JSONB Hybrid Design

  • Engine: PostgreSQL 15, ACID-compliant, Third Normal Form (3NF).
  • 10 Relational Tables: profiles, categories, food_items, addresses, drivers, orders, order_items, driver_locations, notifications, reviews.
  • Hybrid JSONB Implementation:
    • raw_ingredients: Structured JSONB array containing pre-portioned ingredient manifests.
    • cooking_script: Structured JSONB array containing step-by-step chef cooking instructions.
  • Integrity: Purchase-time price locking on order_items ensures historical accounting accuracy regardless of future kit price adjustments.
Speaker Notes: "Our schema combines strict relational constraints for orders with flexible PostgreSQL JSONB columns for cooking scripts and ingredient manifests."
Cloud Security

Kernel-Level Row Level Security (RLS)

  • Database Engine Defense: Authorization policies are executed inside the PostgreSQL database engine, not just in web application middleware.
  • Customer Isolation: SELECT / INSERT on orders and addresses restricted strictly to auth.uid() = user_id.
  • Driver Isolation: Drivers can only access orders assigned to their fleet ID (auth.uid() = driver_id).
  • Admin Access: System-wide operations verified via is_admin() SECURITY DEFINER functions.
  • Public Access: Unauthenticated users can only view available meal kits and category information.
Speaker Notes: "RLS guarantees that even if a client-side API call is tampered with, PostgreSQL rejects unauthorized row queries at the database kernel level."
Real-Time Telemetry

Event-Driven WebSocket Telemetry Pipeline

Traditional Polling Overhead

Client polls every 3s → 1,200 requests/hour/user → Server connection thrashing, high battery drain, and redundant payload transfers.

Supabase Change Data Capture

Driver updates GPS fix → PostgreSQL WAL log emits event → WebSocket pushes coordinates to subscribed customers in ~65ms.

Throttled Location Streaming: The Flutter driver client throttles GPS coordinates to 5–10 second intervals during transit, balancing real-time map accuracy with mobile battery conservation.

Speaker Notes: "Our real-time pipeline uses PostgreSQL Change Data Capture over persistent WebSockets, cutting bandwidth by over 90% compared to legacy HTTP polling."
Serverless Computing

Deno Serverless Edge Functions (FaaS)

  • Execution Model: Event-driven, auto-scaling serverless functions deployed to geographically distributed edge nodes.
  • Key Functions Implemented:
    • create-order: Recalculates cart subtotals server-side to prevent client price tampering.
    • update-order-status: Validates allowed state transitions (Placed → Confirmed → Packaging → En Route → Delivered).
    • assign-driver: Dispatches available online drivers based on proximity.
    • send-notification: Emits cross-platform dispatch alerts.
  • Advantages: Sub-50ms cold starts, zero idle compute charges, and strict sandboxed execution.
Speaker Notes: "Serverless Edge Functions handle trusted business operations. They eliminate client privilege escalation risks and scale automatically from 0 to thousands of requests."

Viva Voce Preparation

Key Technical Defense Questions

Q1: Why choose PaaS over an EC2 monolith VM?

A: Self-hosting requires manual OS patching, cluster replication, and backup configuration. Supabase PaaS provides automated scaling, high availability, and built-in WebSocket replication out of the box.

Q2: How does Row Level Security prevent data tampering?

A: RLS applies authorization rules at the PostgreSQL storage engine level. Even if a user crafts a direct SQL query, rows not owned by that user are completely hidden from the result set.

Q3: Why use WebSockets over HTTP polling for GPS tracking?

A: WebSockets eliminate repetitive TCP/TLS handshake and header overhead (saving ~800 bytes per request), reducing mobile battery drain and latency to under 100ms.

Speaker Notes: "These three questions address the core architectural decisions of our cloud implementation."
